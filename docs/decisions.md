# Decisions

What was decided, when, and why. Newest changes are noted where a decision
replaced an earlier one.

| Topic | Decision | Why |
|---|---|---|
| Hosting | A static site on GitHub Pages; the repo is the database. | No server to run. Every change is a reviewable, revertible commit. |
| Data layout | One YAML file per box and per department, plus settings and a roster. | Readable diffs, and two people editing different boxes never touch the same file. |
| Auth | A pasted fine-grained personal access token (Contents: write on this repo), kept in `sessionStorage`. | Works with no server. An OAuth proxy (e.g. a Cloudflare Worker) could replace it later. |
| Saving (2026-10-03, replaced pull requests) | Save commits straight to `main`, like saving a file. | The team wanted saving to feel like saving a file, not a review step. Each save is still its own commit, so any one can be reverted. |
| Saving through GraphQL (2026-10-04, replaced REST tree, commit and ref writes) | Each save is one `createCommitOnBranch` call, on top of the head the save was checked against; conflicts are found by comparing blob SHAs file by file. | One atomic request instead of a permission check and three writes, and safe to retry: at most one attempt can land, and a lost answer is recognised. GitHub signs these commits "if supported" (its words), which a *Require signed commits* rule needs; that hasn't been checked live with a fine-grained token yet, so BoxOps doesn't promise it works with that rule. |
| Concurrent edits (2026-10-03) | Different items merge automatically. For the same item, the user picks keep mine or keep theirs. A pre-save check shows others' saves for review before writing. | No silent overwrites, and no blocking for the common case. |
| Live updates (2026-10-03) | Open tabs re-check the site's `roadmap.json` every 2 minutes. | Free and unlimited. The GitHub API's anonymous limit also counts "not modified" replies. |
| First load (2026-10-05) | The build parses the roadmap into `roadmap.json` (`parsed`, by path, for its own build only); the YAML parser, saving's code and everything but the timeline are fetched on first use (from 2026-10-06, the GitHub client, a keyboard move, the key and the shortcuts too). | At 2,000 boxes parsing took about 200 ms of every load and the app was one 528 kB file. Now the timeline needs no parsing and a 396 kB file (367 kB from 2026-10-06, leaving room under `npm run perf`'s 400 kB limit); the cost is a `roadmap.json` about 1.7 times the size (310 KB gzipped at 2,000 boxes, from 184 KB; 370 KB when it was by blob SHA). |
| Big timelines (2026-10-05) | A roadmap with more than 300 boxes and PTO blocks draws only the part of the timeline near the screen; each department, and each box, is drawn again only when something in it changes. | At 2,000 boxes the timeline showed in about 870 ms and each drag step or keystroke in the box editor drew all of it again; now about 300 ms, and a step draws one department. The cost: the browser's Find and a screen reader's browse mode reach only what's drawn (the keys reach everything). Up to 300, all of it is drawn: at 300 that shows about 30 ms later, and changes zoom 25 ms slower, than drawing what's near the screen (90 and 40 ms at 600; WebKit on an M1). |
| Big tables (2026-10-05) | A table or People with more than 200 rows (headings, boxes, PTO, engineers) draws only the rows near the screen, and what has focus, with a small hook of our own (`table/useWindowedRows.ts`) rather than a library. Rows of a kind are one height: descriptions and notes show two lines until focused, and People's PTO past two entries folds into "+N more"; a person's row takes one line, or two with notes or PTO past one entry (two kinds, 2026-10-06). | Drawn whole, a table costs about 1 ms a row to open in WebKit on an M1 (250 ms at 250 rows); drawing only what's near the screen, about 50 ms at any size. Rows of one height make the rows not drawn easy to size, so little needs correcting as the table scrolls, and a hook of our own is enough: no new dependency. The cost, as on the timeline: the browser's Find and a screen reader's browse mode reach only the rows drawn, so the table's and People's searches look through every column's text instead (Tab reaches every row). |
| Test hooks in the build (2026-10-05) | `window.__boxopsTest`, which a test sets before the app starts, is in the production build: it turns drawing only what's near the screen on or off, on the timeline (`cull`) and for the table's and People's rows (`virtualize`), and has each department's renders on the timeline, and each row's in the table, counted (`renders`). | The browser tests and `npm run perf` run the production build, as it's deployed, so a hook left out of it couldn't be used; performance marks would be made on every render for every viewer. Without the object, the cost is one property read per department or table row drawn. |
| Lanes | A lane is anonymous FTE capacity (1 or 0.5), not a person. | Plans are about capacity. Who does the work is a separate question. |
| Box FTE (2026-10-03, replaced one box per lane) | A box needs 0.5, 1, 1.5 or 2 FTE and is drawn that tall. Over capacity means more FTE than the lanes on some day. | Multi-person projects in one box. Capacity warnings that match the arithmetic. |
| Engineers (2026-10-03) | Boxes name their engineers, picked from `roadmap/people.yaml` (name, department, role, email, manager, notes), edited in the People tab. | Staffing is visible without tying it to lanes. |
| Working days (2026-10-03) | No weekends anywhere: axis, durations, dragging, date fields, validation. | Plans are made in working days. |
| Repo visibility | Public for now; the roadmap data is part of the public site. A private repo works too (2026-10-04): GitHub Enterprise Cloud can restrict the Pages site to repo readers, and the app reads newer commits through the API with the token (on load, before saving, for racing saves and previews). Without a token it makes no calls to a private repo and shows the deployed copy. | Simplest during development. `raw.githubusercontent.com` can't take a token, so private reads go through the API, fetching only files whose blob SHA changed. |
| Stack | Vite, React and TypeScript in `web/`; Vitest; Playwright with WebKit, and (2026-10-05) Chromium and Firefox; GitHub Actions. | WebKit matches Safari, which the team uses. Chrome, Edge and Firefox must work too, so every browser test runs in their engines as well; the deploy runs WebKit's alone, to go live sooner. |
| Departments and lanes (2026-10-03) | Added, edited, reordered and removed in the app (pencil on a department heading, **+ Add department**). Removing a lane or department that still has boxes requires choosing where they move. | Changing the team's shape shouldn't need a code editor, and should never silently drop work. |
| Box codes (2026-10-03) | Every box has a 3-character code, unique and permanent, shown with its department's code: `DE-A1F`. The prefix follows the department when a box moves. Files store only the 3 characters. | Short, speakable references. A department code change relabels its boxes without rewriting their files. |
| Rules between boxes (2026-10-03) | Boxes can be related: finishes before, starts after, happens during, starts/ends when, runs at the same time as, doesn't overlap. A broken rule shows a popup, red marks and a toolbar list, and never blocks anything. | Dependencies are guidance for planning, like capacity. Plans are sometimes knowingly out of order. |
| Repo scope (2026-10-03) | The repo contains only the roadmap. The earlier Python knowledge-coverage tool (`src/`, `config/`) was removed; it's in history before commit `3d9b821`. | Keep the repo focused. |
